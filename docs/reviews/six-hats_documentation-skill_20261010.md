# シックスハット検討記録：「伝わる文書」スキル

検討日：2026-10-10。
帽子の順序：青（導入）→白→黄→黒→緑→赤→青（統合）。既存の設計案を実行可能なスキルにするため、事実と便益を確認してから欠陥と代案を検討する。

対象：[「伝わる文書」スキル](../../.agents/skills/evidence-doc/SKILL.md)、[記録テンプレート](../../.agents/skills/evidence-doc/references/records.md)、[six-hatスキル](../../.agents/skills/six-hats-brainstorming/SKILL.md)。

## 青帽子｜導入

議題：根拠を調べて理解した内容を説明し、著者以外のレビューと修正・再確認を経て、初任エンジニアと非技術利用者が必要な課題を達成できる文書を作るスキルになっているか。

今回の必須確認は、保存ファイルの構造・リンク、添付原文の保存と移植差分、独立担当による静的レビュー、修正後の再レビュー、失敗しやすい仮想ケースの机上確認。今回の作成対象はスキルであり、アプリ文書の全面改訂・対象実機での実証は別の試行工程とする。

## 白帽子｜事実

### 既知の事実

- ユーザーは、技術名の一行説明ではなく、公式資料・実装を調べた仕組みの説明と、他者による批判・改善を求めている。
- 作成した文書作成スキルは、調査、初稿、独立レビュー、six-hat、作業・理解の検証、修正、再レビュー、完了判定を規定する。
- ユーザー添付のsix-hatスキルを読んで移植した。原文は別ファイルへ保存し、添付の展開内容とバイト単位で一致した。SHA-256は `374df3da246389b1b5cb1458d19d2cd6c5d570f9bb2f1e6360ddb0dcef5b2319`。
- 主な移植差分は実行AI名と保存・提示方法。適用範囲と、独立レビューは別工程である旨も追記した。
- 初任実行者、根拠監査、運用の3担当を独立に起動し、保存ファイルをレビューした。著者の自己評価と他担当の結論は初回に渡していない。
- 3担当とも修正版を再読した。指摘した範囲では重大な残存問題を報告しなかった。

### 未確認の事実

- 実読者が本スキルの成果物を理解できるか。
- このスキルによるアプリ文書の全面改訂を完了し、実機で検証できるか。
- 異なるリポジトリ・言語・実行AIでも十分に運用できるか。
- 実行クライアントが新しいファイルを自動でスキル一覧へ登録するか。ファイルの作成と自動登録は別に扱う。

### 必要な追加情報

- 実案件で使ったときの課題結果、追加説明が必要になった箇所、工程の負担。
- 対象利用者と対象機器での試読・操作結果。

## 黄帽子｜便益

- 技術説明を定義から入出力・処理・具体例・限界までつなげる規定がある。根拠を調べて各項目を実装へ対応させる場合、一行定義による説明の飛躍を発見できる。
- 独立担当の課題が異なるため、式の正しさだけでなく操作・理解・根拠の問題を検討できる。担当が実際に保存物を読み、確認範囲を報告することが成立条件。
- 再確認と未完了の扱いがあるため、指摘を書いて終わることや、未実施項目を成功扱いすることを防ぐ判断材料になる。
- 添付原文を保持して移植しているため、元の手順と環境依存の調整を比較できる。

## 黒帽子｜問題

1. **最も強い懸念：読者役が一次資料や既有知識で説明不足を補う。** 初稿は全担当へ一次資料を渡す指示と、文書外の補完を認めない指示の関係が弱かった。正答が出ても本文の理解可能性が証明されず、元の問題が残り得る。
2. **説明だけの修正を軽微な文面修正として閉じる。** 初稿の再実行条件は作業・計算への影響が中心で、仕組みの説明改訂後の理解確認が曖昧だった。
3. **重要概念や必須確認を後から選び直す。** 初稿では概念と読者課題の対応、実機・実読者確認の要否を記録する欄が弱く、実施不能な確認を外して完了扱いする余地があった。
4. **動作を精度と誤認する。** 模擬検証の区別はあっても、実カメラで骨格が表示された事実から精度まで確認済みとする判断を防ぐ規定が弱かった。
5. **保存と再現を混同する。** コードを保存しても一時環境の依存が残れば、後任は再実行できない。
6. **担当不在や章間状態の照合を記録できない。** 代替経路への参照と、前章の終了状態・次章の開始条件の記録が初稿では弱かった。

## 緑帽子｜代案

- 技術概念と読者課題を対応付け、正常・境界・失敗の理解課題を用意する。
- 根拠監査と読者役へ渡す資料の範囲を分け、回答に使った文書外の情報を記録する。
- 動作、精度、保存、再現、実読者の理解を、それぞれ別の確認状態として記録する。
- 文書を読むだけの方法に加え、読者が処理を他者へ説明し、別の条件を判断する対話教材を試す。これは文書の項目を増やす方法とは異なる選択肢である。

## 赤帽子｜直感

以下は実読者の感想ではなく、検討担当AIによる直感。

- 六つの見出しを埋めれば十分という安心感には違和感がある。
- 正しい式だけが並んだ文書を渡されると、変更する判断には不安が残る。
- 分からなかった箇所を失敗として記録できる進め方には安心感がある。

## 青帽子｜統合

### 論点の対立と判断

- 多数の観点でレビューする便益と、共通の思い込みが残る懸念が対になる。レビュー人数より根拠照合と未掲載課題を優先し、合意だけで合格にしない。
- 資料を広く参照する便益と、最も強い懸念である本文不足の補完が対になる。監査担当には一次資料を渡し、読者役には事前指定した参照範囲を渡す。補完して正答した場合は本文の理解確認を合格にしないよう修正した。
- 丁寧な再確認と不要な反復の負担が対になる。式・操作が不変でも説明・前提・判断を変えた場合は理解課題を再実行し、無関係なテストは繰り返さない。
- 今回は対話教材の実装まで広げず、未掲載課題と読者の説明による検証を最小の試行方法として採用する。実案件の結果で再評価する。

### 検証結果と再現方法

スキル本体・付属資料4個と本記録を合わせた5個のMarkdownファイル、2個のスキル定義、ローカルリンク6件を確認。コードフェンスと表の列数も照合した。添付の原文とのバイト照合を実施し、現行six-hat本文からこの環境で利用できない保存先・提示ツール・特定AI名を除いたことを確認した。アプリの追跡ファイルに差分はなかった。

保存物の構造とリンクの確認は、リポジトリのルートで次を実行できる。

```bash
python3 - <<'PY'
from pathlib import Path
import re, hashlib
root = Path('.agents/skills')
files = list(root.rglob('*.md'))
for p in files:
    text = p.read_text()
    if p.name == 'SKILL.md' and p.parent.name != 'references':
        m = re.match(r'^---\nname: ([a-z0-9-]+)\ndescription: ([^\n]+)\n---\n', text)
        assert m and m[1] == p.parent.name and len(m[2]) <= 1024, p
    for target in re.findall(r'\[[^\]]+\]\(([^)]+)\)', text):
        if '://' not in target and not target.startswith('#'):
            assert (p.parent / target.split('#')[0]).resolve().exists(), (p, target)
original = root / 'six-hats-brainstorming/references/original-SKILL.md'
assert hashlib.sha256(original.read_bytes()).hexdigest() == '374df3da246389b1b5cb1458d19d2cd6c5d570f9bb2f1e6360ddb0dcef5b2319'
active = (root / 'six-hats-brainstorming/SKILL.md').read_text()
assert all(x not in active for x in ('/mnt/user-data/outputs/', 'present_files', 'Claude'))
print('Skill metadata, local links, original integrity, and platform adaptation: OK')
PY
```

これは構造と保存の確認であり、文章の正確さ、実読者の理解、別案件での有効性を自動判定するものではない。

保存後、根拠監査担当が上記スニペットをリポジトリルートでそのまま再実行し、終了コード0で成功した。追加の非記載依存や補助コードは不要だった。これは別担当による保存物の構造・整合性の再現確認である。

### 次の一手

文書作成担当がこのスキルを使い、元の仕様説明書・使用マニュアルの改訂で試行する。開始時に読者課題と必須確認を設定し、終了時に課題結果と追加説明が必要だった箇所を本スキルへフィードバックする。実機と実読者の確認は、利用できる担当・環境と必須条件に応じて実施し、未実施ならその状態を残す。
