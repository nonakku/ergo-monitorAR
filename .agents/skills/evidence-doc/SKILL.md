# 伝わる文書

根拠調査・複数視点レビュー・理解検証。

目的は、初めて読む人が仕組みを理解し、必要な作業を完了し、条件が変わっても判断できる文書を作ること。文量、引用数、レビュー人数を完成の証拠にしない。

## 適用と境界

- ユーザーが指定した成果物・対象・詳しさ・除外範囲を最優先する。レビューだけの依頼では、無断で本文の改訂や機能変更へ進まない。
- 実装・公式資料・実行結果を調べる。想像で技術説明、設計意図、性能要件、画面、検証結果を補わない。
- 文書化のためにアプリの機能・計算式を変更しない。変更案は改善提案として区別する。
- このスキルは**著者以外の独立したレビュー担当を使う**。サブエージェントが利用可能なら、少なくとも2担当を別のコンテキストで起動する。役割の演じ分けだけで独立レビュー済みにしない。
- 独立レビューを実施できない場合は、代替として役割別に点検し、独立レビュー未実施と報告する。「検証完了」の条件は満たしていないと扱う。
- 実読者による理解確認と、AIによる読者役の確認は分ける。

## 0. 作業を定義する

1. リポジトリの指示ファイル、既存文書の配置、作業中の差分を確認する。対象コミット、確認日、対象コード、外部依存を記録する。
2. 読者ごとに目的、前提知識、利用環境、操作権限を定義する。既知でないことを「常識」として省略しない。「誰でも分かる」は読者別の課題に置き換える。
3. 成果物の保存先を既存配置から決める。仕様書・利用者向け文書・根拠と検証記録の役割を分け、相互にリンクする。
4. 読者課題と合格条件を執筆前に決める。初任エンジニアなら起動、主要処理の説明、新しい入力での計算、変更箇所と影響先の特定、障害調査。利用者なら準備、開始、操作、結果の理解、復旧、終了。各課題について、必須／任意、確認する環境、実機・実読者の要否、代替の可否を記録する。実施できなかったことを理由に必須条件を後から任意に変えない。条件の変更が必要なら理由と依頼との整合を示し、ユーザーの判断が必要な変更だけを確認する。
5. 調査で解決できる疑問を先に調べる。ユーザーの判断だけが必要な事項を一度に一問ずつ聞く。回答に依存しない調査は進める。

コード調査から、操作、結果の解釈、変更、障害調査に影響する技術・概念を一覧化する。それぞれを説明の7項目と読者課題へ対応付け、正常時だけでなく境界・未検出・失敗等の判断も合格基準に含める。

[記録テンプレート](references/records.md)を読み、読者課題、根拠、検証、レビュー、未解決事項の記録を用意する。既存形式があれば、それを使ってよい。

## 1. 実物と公式資料を調べる

既存資料→コードと設定→依存関係と採用版→起動と画面→公式資料の対応→計算と例外の順で、相互に照合する。順番は依存に応じて調整してよい。

### コードと履歴

- エントリーポイント、呼出関係、状態、データの流れ、保存、権限、外部通信、終了と例外処理を追う。
- 説明と実装に矛盾があれば両方を確認し、現在の挙動と既存資料の記載を区別する。解決できない矛盾は場所と影響を残す。
- 設計意図・採用理由は履歴、議論、設計記録等から確認する。動作を見て考えた合理的な理由を、実際の採用理由として書かない。記録がなければ未確認とする。
- 変更してはいけない契約、変更可能な設定、依存して更新する箇所、確認が必要な判断を整理する。

### 技術と資料

- 依存の名称だけでなく、採用版、API世代、同梱方法、必要資産、ライセンス、更新方法を確認する。外部実装の監査は依頼と説明に必要な範囲に限定する。
- 初めて扱う技術は公式資料を読んで仕組みを理解する。取得したことやURLを並べたことだけで調査済みにしない。
- 最新版の資料を旧版へ無条件に適用しない。採用版の型・コード・配布物を併用し、説明の適用範囲を示す。
- 引き継ぎに必要な資料は許容される範囲で原文または抜粋を保存し、出典、版またはコミット、取得日を記録する。取得できなかった資料、未保存の画像やリンク先も明記する。
- 認証情報や秘密値を記録しない。必要な設定名、意味、取得・設定方法を説明する。

### 状態と根拠を別に扱う

| 分類 | 表記する内容 |
| --- | --- |
| 実装状態 | 実装済み／未実装／該当なし／対象外 |
| 確認状態 | 確認済み／未確認。確認した条件と範囲を併記 |
| 根拠の種類 | コード確認／資料確認／実行確認／ユーザー提供情報 |
| 今後の案 | 改善提案。現状の実装と混同しない |

「コード上にある」と「動作を確認した」を分ける。重要な記述にはコード位置、資料の該当箇所、または検証記録を対応付ける。

## 2. 仕組みを説明する初稿を書く

### 説明の深さ

重要な技術・業務概念は、以下をつながった説明にする。

1. 何か。どんな問題を扱うものか。
2. このシステムでは何を担当するか。
3. 入力・出力・単位・基準は何か。
4. 主要な処理と、他の要素との接続はどうなっているか。
5. 具体例を追うと何が起きるか。
6. 成立条件、限界、異常時の挙動は何か。
7. 実装と根拠をどこから確認できるか。

技術名＋一行定義、APIの羅列、コードの日本語化だけで済ませない。必要な専門用語を初出で説明し、その説明に出てくる新しい用語も点検する。基本説明→処理の流れ→具体例→詳細・根拠へ進む構成にする。

例えば姿勢推定を使う場合は、画像から身体の点が得られるまで、モデル・検出・追跡の役割、出力座標と信頼度の意味、実行基盤の関係、アプリ固有の計算への接続を説明する。ライブラリが姿勢を推定することと、アプリが評価点を計算することを区別する。

### 引き継ぎ仕様書

- 目的、対象、利用場面、実装済み・未実装機能、制約。
- 構成と技術、主要ファイル、起動から終了の処理・データの流れ、画面と状態遷移。
- 環境準備、取得する版、必要ツールの確認、起動・ビルド・テスト、成功条件と終了方法。該当しない工程はその理由を示す。
- 設定値の意味と変更の影響、保存先・形式・期間・取得と削除、権限・認証・映像や個人情報の扱い。
- エラーとログ、切り分けと復旧、確認結果、既知の問題、未解決事項、変更時に一緒に確認する箇所。
- 確認できた設計意図と制約を示す。後任が変更を判断するための材料を残す。

計算は入力、取得、前処理、式、単位、重み、閾値、丸め、欠損・異常・境界、結果の意味と限界、実装と一致する例を記載する。採用理由と出典は確認できたものだけを書く。複数の点数体系や色の基準を混同しない。

全変数・全関数の一覧を求められた場合は、対象と除外を明示し、一時変数、引数、ループ、catch、匿名関数も定義位置で識別する。可能ならAST抽出、その他は言語に応じた抽出と手動照合を行う。網羅性だけでなく各項目の意味もコードと照合する。

- 変数：名前、位置、スコープ、型、意味、単位、初期値、範囲、更新条件、使用箇所。
- 関数：名前、位置、役割、引数、戻り値、副作用、呼出元、エラー時の挙動。
- 確定できない値は未確認とし、公式の期待範囲と実装による強制・保証を分ける。

### 利用マニュアル

- 機器、OS、ブラウザー、カメラ、通信、アカウント・権限、配布一式、インストールの要否を先に示す。利用者と管理者の準備を分ける。
- 確認した環境、資料にある要件、未確認環境を区別する。未計測の最低・推奨性能を作らない。
- 実際の画面・ボタン・入力名に合わせ、各手順に開始条件、操作、成功の表示、次の操作を示す。
- 初回準備、通常利用、再開、終了を連続して実行し、前章で変更した状態と次章の前提を照合する。
- 専門用語、角度の基準、入力を選ぶ判断方法を説明する。判断ルールが確認できなければ調査し、未解決の箇所は明記する。
- 数値・色・判定の意味、使える範囲、更新停止や残留値の見分け方を説明する。
- 保存・出力・再表示、症状別の対処、解決の目安、問い合わせ情報を示す。未実装も明記する。
- 画像は実際に取得した画面を使い、取得条件を示す。取得できない場合は架空の画面を作らない。
- ユーザー提供の既知トラブルを落とさない。実機検証済みと混同せず、原因・程度・設定場所を根拠なく補わない。

## 3. 著者以外が独立にレビューする

著者と同じ説明を知っているだけの読み直しで完成させない。初稿を保存し、次の担当を使う。

| 担当 | 主な課題 |
| --- | --- |
| 初任エンジニア | 仕組みを説明し、起動・計算・修正箇所・障害調査をたどる。未知の技術を理解できるか確認する |
| 利用者・運用担当 | 準備から終了まで実行し、入力と結果を判断する。隠れた前提と操作の矛盾を探す |
| 根拠監査担当 | 重要な記述をコード・採用版資料・実行結果と独自に照合する。推測、版違い、検証範囲の過大表現を探す |

エンジニア向けと利用者向けの両方なら上記3担当、片方だけなら対象読者担当と根拠監査担当の最低2担当を使う。並行可能なら別々にレビューさせる。

根拠監査担当には保存した初稿、対象リポジトリ、読者課題、制約と必要な一次資料を渡す。理解確認の読者役には、文書と課題ごとに事前指定した参照範囲を渡す。コードや外部資料の読解を読者に求める場合は、その範囲と必要な前提知識を文書に明示する。外部資料で本文の不足を補って正答した場合は、本文だけで理解できたと扱わない。

著者の「十分説明した」という評価や、他担当の結論は初回レビュー前に渡さない。担当が用いる資料と独自調査の範囲を記録する。独立担当を利用できない場合の扱いは「適用と境界」に従う。

指摘は「場所／問題／具体的な失敗例／根拠／影響／修正案／再確認方法」で記録する。単なる好みと、事実誤認・操作不能・説明の欠落を区別する。同じモデルに由来する見落としは残り得るので、多数決を事実の証拠にしない。

## 4. six-hatで問題と改善案を検討する

同梱の [six-hats-brainstorming](../six-hats-brainstorming/SKILL.md) を読み、保存済みの初稿と独立レビューの指摘を議題にして適用する。最初の使用時はユーザーへ知らせる。

議題は「対象読者が必要な理解と作業を完了できるか」。六つの帽子は思考観点、前節の担当は読者・監査の役割であり、六つの見出しを書くだけで独立レビュー済みにしない。

- 白：実装・資料・実行から確認した事実、未確認事項、足りない情報。
- 赤：読者が感じる迷い・違和感。実読者の感想とAIによる推定を分ける。
- 黄：役立つ説明と、その成立条件。修正時に保持すべき長所。
- 黒：誤解、誤操作、引き継ぎ不能を生む箇所。根拠と影響。
- 緑：説明例、図、導線、検証方法等の代案。アプリ変更案は別の改善提案とする。
- 青：対立を根拠と読者課題で判断し、最も強い懸念への対応、修正と再確認の順序を決める。

記録を保存する。全帽子の合意を合格条件にしない。解決しない意見の相違は、理由と判断に必要な情報を残す。

## 5. 作業と理解を検証する

### 作業の再現

文書の手順を、そこに記載された前提と対象物を使って実行する。著者の口頭補足や、文書にない補助コードで不足を埋めない。リンク先のコード・資料を読む課題なら、その参照は許可する。追加情報が必要になった場所を記録する。

起動、操作、画面名、出力、終了を照合する。障害は可能な範囲で再現し、注入した模擬エラーと実障害を区別する。外部通信、保存、権限、復旧の確認は対象機能に合わせる。

### 理解の確認

「分かりましたか」だけで判定しない。掲載例と異なる入力や状況を使い、読者役が理由と次の操作を説明できるか確認する。

- 計算：未掲載の境界値を含む入力で結果を求め、実関数と照合する。
- 構成：入力から出力までを説明し、各技術とファイルの担当を示す。
- 開発：仮の変更要求について修正箇所、影響先、確認方法を示す。文書化のために機能を変更しない。
- 利用：正常表示と古い値・未検出・停止を区別し、次の操作を判断する。
- 障害：異なる症状について確認する情報と切り分けの順序を示す。

読者役の回答を見る前に、監査担当は実装等から期待結果と採点基準を用意する。著者の模範解答を読者役へ先に渡さない。答えが合っていても、文書外の知識で補った場合は文書の理解可能性が未確認とする。

AIによる確認で実読者の理解を保証しない。実機、模擬カメラ、合成入力、エラー注入、AI読者役の確認範囲をそれぞれ明記する。

動作確認と精度評価を区別する。実カメラで結果が得られただけでは精度確認済みにしない。精度を主張する場合は、正解データまたは比較基準、測定方法、評価指標、条件、合格閾値を定め、実測結果を示す。それらがなければ精度未確認とする。

再現に必要な検証コード・入力資産・依存版・モデル・コマンド・期待結果をリポジトリの適切な場所へ保存する。別担当が保存物と文書に明示した環境から再実行し、一時環境の隠れた依存がないか確認する。実行できない場合は、保存済みと再現確認済みを区別する。使い捨ての環境にしかないテストを、後任が実行可能と書かない。

低影響の誤字・表記修正は、根拠照合と読み直しで検証してよい。技術の仕組み、前提、結果の判断を修正した場合は、式や操作が変わっていなくても関連する理解課題を再実行する。

## 6. 修正して再レビューする

1. 指摘を事実誤認・主要手順の実行不能・重要な説明欠落・読みやすさに分け、影響の大きい順に修正する。
2. 修正に新しい主張が含まれる場合は、その根拠を調べる。反論を文章で追加するだけで指摘を解消済みにしない。
3. 修正後の保存ファイルを読み直す。コード位置、根拠、例、用語、図、リンク、他文書との整合を確認する。
4. 著者以外の担当へ修正版を渡し、修正した問題と影響範囲を再確認させる。作業・計算・理解に影響した場合は関連課題を再実行する。独立担当を利用できない場合は再レビュー未実施として残し、検証完了にはしない。
5. 通常は「初稿→独立レビュー→修正→再レビュー」の一巡を最低限とし、重大な問題が残れば次の一巡へ進む。回数を満たしただけで完成にしない。新たな理由なく同じテストを繰り返さない。

## 7. 完了判定・保存・報告

以下を確認して判定する。

- 読者課題に必要な前提、仕組み、操作、成功条件が説明されている。
- 重要な記述と計算例が根拠と一致し、対象コードへたどれる。
- 求められた一覧が対象コードと照合され、網羅性の方法と除外が明記されている。
- 実行可能な主要手順を確認し、未実行項目と理由を明示している。
- 独立レビューとsix-hatの指摘に対応と再確認結果がある。
- 主要課題を妨げる文書上の誤り・矛盾が残っていない。
- 現状のアプリ不具合と文書不備を区別し、利用できる範囲と未解決事項を説明している。
- 保存した成果物を再読して照合している。

「文書作成済み」「可能な範囲の検証済み」「必要条件の検証完了」を区別する。独立レビューや対象環境での必須確認ができない場合は検証未完了と報告し、完了に必要な条件を示す。利用できる範囲を正確に説明できているアプリの既知不具合は、文書作成自体の未完了と混同しない。

文書本体、根拠、検証手順・必要コード、レビューと修正の記録を保存する。対象版、確認日、更新の契機、担当または担当未定を残す。関連コード、モデル、計算、UI、起動、権限、環境が変わったときに見直す項目を示す。

最後に保存場所、確認したこと、確認できなかったこと、未解決事項を簡潔に報告する。コミット、公開、配布、インストール済みという状態を、実施せずに宣言しない。
